# Repository Hygiene and Git Safety Rules

These rules are mandatory for every Devin task in this repository.

## Core Principle

The production Git repository must contain only files that are intentionally required for:
- application source code
- runtime
- build
- deployment
- CI/CD
- intentionally versioned development configuration
- intentionally versioned documentation

Do not commit or push internal, temporary, generated, diagnostic, testing, agent, investigation, or local-only artifacts unless their inclusion is explicitly justified.

## Before Creating Any New File

Before creating a new file or directory, determine whether it is:
1. required by production/runtime/build/deployment,
2. intentionally versioned project documentation/configuration,
3. temporary/local-only output.

If it is temporary or local-only:
- do not place it in a tracked production path when avoidable;
- prefer a clearly local/ignored location;
- verify or update `.gitignore` before generating the file.

## Mandatory Pre-Commit Hygiene Check

Before every commit or push, inspect all changed, untracked, and newly added files.

Run or equivalent:
- `git status --short`
- `git diff --cached --name-status`
- `git ls-files --others --exclude-standard`

Review every new file.

Do not commit a file merely because it exists in the working tree.

## Never Commit by Default

The following must not be committed unless the user explicitly approves and there is a verified repository requirement:

- `.env`
- `.env.*` containing real secrets
- credentials
- API keys
- tokens
- private keys
- production environment values
- local databases
- `*.sqlite`
- `*.sqlite3`
- database dumps
- temporary database copies
- debug output
- build logs
- error logs
- screenshots created for debugging
- progress screenshots
- temporary images
- generated investigation artifacts
- local test output
- temporary JSON/TXT parameter files
- local query/result files
- ad-hoc scripts used only for one investigation
- AI-generation intermediate files
- browser automation screenshots
- internal evidence reports
- internal investigation reports
- private project-memory artifacts
- customer/user data
- copied production data
- OS/editor temporary files
- malformed or accidental files created by shell commands

Examples include names such as:
- `db_test.sqlite3`
- `db_check.sqlite3`
- `build_output.txt`
- `*_error.txt`
- `hero-progress-*.png`
- temporary `query` files
- accidental malformed filenames

## project-memory and evidence

Treat `project-memory/` and especially `project-memory/evidence/` as INTERNAL by default.

Do not add, commit, or push:
- investigation reports
- validation reports
- implementation evidence
- debugging evidence
- internal audit reports

unless the user explicitly requests that a specific file be version-controlled.

If these reports are needed locally, keep them local and ensure they are ignored by Git.

## Agent and Tool Artifacts

Do not automatically commit files or directories generated by:
- Devin
- coding agents
- browser automation
- AI tools
- visual-generation tools
- temporary test harnesses
- one-off debugging workflows

Agent/tool configuration should only be versioned if it is intentionally part of the project workflow.

Do not assume directories such as `.agents/`, `.devin/`, generated skills, temporary workflows, or tool locks belong in production Git. Verify first.

## Reference and Experimental Directories

Before committing experimental, reference, copied, generated, or design directories:
- prove they are referenced by runtime/build/import/config code;
- otherwise keep them outside Git or remove them from tracking.

Never keep an entire reference/template directory in production simply because one task used it temporarily.

## .gitignore Responsibility

Whenever a task creates a new category of local/generated artifact:
1. inspect `.gitignore`;
2. add a safe ignore rule if appropriate;
3. verify the rule with `git check-ignore -v <file>`;
4. make sure the rule does not hide required source files.

Do not use overly broad ignore rules that could hide legitimate application code.

## Sensitive Data Check

Before every commit/push, check newly added or modified files for:
- credentials
- secrets
- tokens
- private URLs
- internal infrastructure details
- real database contents
- personal/customer data

Never print secret values in reports.

If sensitive data is found:
- stop;
- do not commit or push;
- report only the file/path and type of exposure;
- remove/rotate credentials when necessary.

## Git Tracking Rule

A file being present locally does NOT mean it should be tracked.

A file already committed in the past does NOT mean it is acceptable to keep.

If a tracked file should be local-only:
- remove it from Git tracking safely;
- preserve the local copy when appropriate;
- add the required `.gitignore` rule.

## No Blind Staging

Do not use broad staging such as:

`git add .`

or

`git add -A`

without reviewing the complete resulting staged file list first.

Prefer staging intentional files or clearly reviewed groups of files.

After staging, always inspect:

`git diff --cached --name-status`

and verify every path.

## Production Repository Review Before Push

Before every push, confirm:

- no secrets are included;
- no `.env` with real values is included;
- no local database is included;
- no debug/test artifacts are included;
- no internal evidence/report files are included;
- no accidental screenshots are included;
- no temporary agent/tool files are included;
- no malformed accidental files are included;
- all newly added dependencies/config files are intentional;
- `.gitignore` is adequate;
- production build/runtime files remain intact.

If any suspicious new file is present, stop and investigate it before pushing.

## Dependency and Cleanup Safety

Never delete or untrack a suspicious file solely based on its name.

Before removal:
- search the repository for references;
- check build scripts;
- check runtime imports;
- check Railway/deployment configuration;
- check CI/CD;
- check backend/frontend scripts.

Production functionality takes priority over cleanup convenience.

## Required Final Check

At the end of every implementation task that changes files, include a repository hygiene check in the task validation.

Explicitly report:
- new files created,
- files deleted,
- files added to Git,
- `.gitignore` changes,
- whether any temporary/local artifacts remain,
- whether the staged changes contain only intentional production/project files.

If repository hygiene is uncertain, do not push until it is resolved.
